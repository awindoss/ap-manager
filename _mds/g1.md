## 二、严重问题：连接泄漏

这是必改项。

### 问题描述

def connect(self) -> sqlite3.Connection:
    conn = sqlite3.connect(str(self.db_path))
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA foreign_keys = ON;")
    return conn

  所有 CRUD 都用：



with self.connect() as conn:
    ...
  关键点：在 Python 里，with conn: 只管理事务（commit / rollback），不关闭连接。

也就是说：

- 每次 add_node / get_node / add_edge / get_children / get_parents / ... 都会新开一个 SQLite 连接；
- 这个连接在 with 退出后不会被关闭；
- 只能等垃圾回收时才可能被回收；
- 在 CPython 里靠引用计数能回收大部分，但：

  - 有循环引用或异常时会延迟；
  - 大量调用时文件描述符可能被耗尽；
  - 未来若换成 PyPy、或引入线程，问题会放大。

对一次 GUI 会话来说不算立刻炸，但对 get_all_positions、would_create_cycle 这种递归调用来说会成倍放大。

### 演示

例如 would_create_cycle：




while queue:
    current = queue.pop(0)
    ...
    children = self.get_children(current)  # 每次调用开一个新连接
    queue.extend(children)
  对一个有 N 个节点的图，会开 O(N) 个连接且都不关闭。

get_all_positions 同理：每层递归都调用 get_parents，每次都开新连接。

### 建议改法

方案 A（推荐）：加一个上下文管理器，按需开关连接




from contextlib import contextmanager

@contextmanager
def connection(self):
    conn = sqlite3.connect(str(self.db_path))
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA foreign_keys = ON;")
    try:
        yield conn
        conn.commit()
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close()
  然后把所有 with self.connect() as conn: 改成：




with self.connection() as conn:
    ...
  保留 connect() 作为“只返回连接”的底层 API 也可以，但要让内部 CRUD 用 connection()。

方案 B：保留长生命周期连接




def __init__(self, db_path):
    ...
    self._conn = sqlite3.connect(str(self.db_path))
    self._conn.row_factory = sqlite3.Row
    self._conn.execute("PRAGMA foreign_keys = ON;")
  但这与 Qt 主线程 / 未来多线程会冲突，且需要处理关闭时机。对当前阶段来说，方案 A 更稳。

方案 C：至少显式 close




conn = self.connect()
try:
    with conn:
        ...
finally:
    conn.close()
  也可以，但写法啰嗦。推荐 A。

## 三、中等问题

### 1.`would_create_cycle`与`get_all_positions`的连接开销

即使修好连接泄漏，这两个算法依然会开 O(N) 个连接。对一个几千节点的图来说是明显卡顿。

建议：算法内部接受一个 conn 参数，或者提供一个内部方法 _get_children(conn, parent_id)，把连接复用。

例如：



def _get_children_with_conn(self, conn, parent_id):
    sql = ...
    rows = conn.execute(sql, (parent_id,)).fetchall()
    return [row[0] for row in rows]

def would_create_cycle(self, parent_id, child_id) -> bool:
    if parent_id == child_id:
        return True
    with self.connection() as conn:
        visited = set()
        queue = [child_id]
        while queue:
            current = queue.pop(0)
            if current == parent_id:
                return True
            if current not in visited:
                visited.add(current)
                queue.extend(self._get_children_with_conn(conn, current))
    return False
  这样每次 would_create_cycle 只开一次连接。

get_all_positions 同理，把 get_parents 换成传入 conn 的内部版本。

这一项不阻塞 Phase 1，但建议和连接问题一起顺手做掉，因为改一次比改两次便宜。

### 2.`add_edge`返回类型可能为`None`



cursor = conn.execute(sql, (parent_id, child_id, sort_order))
return cursor.lastrowid
  lastrowid 类型标注是 int | None。实际运行会返回 int，但类型检查器会报警。可以：




new_id = cursor.lastrowid
if new_id is None:
    raise sqlite3.Error("Failed to retrieve new edge ID")
return new_id
  或者标注 -> int 加 # type: ignore。属于小问题。

### 3.`add_edge`的 IntegrityError 捕获过粗



except sqlite3.IntegrityError:
    log_error(f"Edge {parent_id} -> {child_id} already exists or invalid ID.")
    raise
  IntegrityError 既可能是 UNIQUE 冲突，也可能是 FOREIGN KEY 失败。业务层无法区分“重复关联”和“节点不存在”。建议分开：




except sqlite3.IntegrityError as e:
    msg = str(e).lower()
    if "unique" in msg:
        log_error(f"Edge {parent_id} -> {child_id} already exists.")
    elif "foreign key" in msg:
        log_error(f"Edge {parent_id} -> {child_id} references non-existent node.")
    else:
        log_error(f"IntegrityError on edge: {e}")
    raise
  对 Phase 1 不致命，Phase 5 用得多，可以先记着。

### 4.`get_all_positions`的循环处理方式




if p_id in current_path:
    log_error(f"Detected loop during path generation around node {p_id}")
    continue
  这是对的。但如果数据库里真有环，会静默返回一个不完整的路径集。建议同时在 log_error 里带上 current_id 和 node_id，方便排查：




log_error(f"Loop detected: node={node_id} current={current_id} parent={p_id} path={current_path}")
  另外语义上，环检测已经在 would_create_cycle 里做了，get_all_positions 里遇到环属于数据损坏，考虑加“logger + 上抛”而不是静默跳过。当前静默可接受，但请明确这是“兜底”而非“正常流程”。

## 四、小问题

1. node.id / edge.id 默认值：




id: Optional[int]
  建议 id: Optional[int] = None，这样 Node(name="X") 可以直接构造，不必每次传 id=None。属于风格统一问题。
2. delete_node 的错误处理信息：




log_info(f"Completely deleted node {node_id} and its associated edges.")
  只有成功信息，没有失败。目前失败走 log_error + raise，可以接受。
3. update_node 对无效 key 静默忽略：




if key in valid_fields:
    ...
  如果用户传了 style_colorr（拼错），会被静默忽略，行为难以调试。可以加一个 else 分支 log_warning，或者抛 ValueError。Phase 1 不强制，但建议记着。
4. get_root_nodes 用 NOT IN 子查询：在 edges 表很大时性能不如 LEFT JOIN ... WHERE child_id IS NULL。但因为有 idx_edges_child，目前可接受。规模大了再换。
5. init_tables 的 with self.connect() as conn：和 CRUD 一样的问题，但 init_tables 只调用一次，影响小。修连接问题时顺手改掉即可。
6. from utils import constants 后大量 constants.XXX：可读性略差，但没有问题。可以接受。
7. db_path.parent.mkdir(parents=True, exist_ok=True) 放在 __init__：很好，符合“目录自动创建”的要求。但注意这也意味着只要构造 Database 就会创建 data/ 目录。将来如果要在 main.py 里先做可写性检查，需要注意这个副作用。
